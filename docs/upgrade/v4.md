# Upgrading to Agent Blueprint v4

Agent Blueprint v4 is the same set of pipelines running in eight coding CLIs (Claude Code, Codex, Antigravity, Grok Build, Pi, Cursor CLI, Hermes and Amp): every skill is named `ab-`, the agents live inside the skills as prompt files instead of an `agents/` directory, and the project instructions file is `AGENTS.md`.
It is a clean break from claude-code-blueprint v3.8.0: the repository, the plugin id, the skill names and the working folders all change, and this guide maps each one.
A v3 project keeps working as it is until you migrate it; nothing in v4 touches a project until you run the steps below.

## Before you start

- Commit or stash your work. The migration refuses to run on a repository with uncommitted changes, because its backup only protects committed work.
- Note the installed v3 version with `claude plugin list`, so a rollback knows what to reinstall.
- The migration creates a branch `blueprint-v3-backup` at the current commit before it removes anything, so every removed file stays one checkout away.

## Step 1: install v4

In Claude Code:

```bash
claude plugin marketplace add Ninety2UA/agent-blueprint
claude plugin install agent-blueprint@agent-blueprint
```

From a checkout, `bash install.sh` runs the same two commands with the local path and also installs for every other tool it finds. The other seven hosts each have their own route; see the support notes under `docs/hosts/` (`claude-code.md`, `codex.md`, `antigravity.md`, `grok-build.md`, `pi.md`, `cursor-cli.md`, `hermes.md`, `amp.md`).

The new plugin id is `agent-blueprint@agent-blueprint`. The old one, `claude-code-blueprint@claude-code-blueprint`, stays installed until you remove it in Step 3, so for now both sets of skills load; the v4 session-start hook warns in every Claude Code session until the old plugin is gone, and `install.sh` warns when it finds it.

## Step 2: clean the project with ab-migrate

Run the ab-migrate skill in each project that used v3. It is manual-only: no host starts it from a description, you have to name it. It runs its bundled `scripts/detect-v3.sh`, which reports one line per trace and changes nothing until the skill applies the list. Only files the blueprint itself installed count as traces:

| Trace | What happens to it |
|---|---|
| `.claude/skills/<name>/` and `.claude/commands/<name>.md` where `<name>` is a v3 skill in the name map | removed |
| `.claude/agents/<name>.md` for the 29 v3 agent names, and the v3 hook handler files under `.claude/hooks/` or `hooks/handlers/` (with a `hooks/hooks.json` that points at them) | removed |
| `scripts/ship.sh` when it is the blueprint's copy | removed |
| `.claude-plugin/plugin.json` named `claude-code-blueprint` | removed |
| `.claude/ship-*.local.md` and `.claude/team-active.local.md` | moved to `.agent-blueprint/run/v3/` |
| `CLAUDE.md` as a regular file with no `AGENTS.md` | renamed to `AGENTS.md`; a new one-line `CLAUDE.md` containing `@AGENTS.md` imports it |
| The v3 plugin still installed in Claude Code | reported with its uninstall command; never removed by the skill |

Files the blueprint did not install are never touched: your own skills, agents, hooks and scripts stay where they are. Other skill packs ship files with some of the same names (`brainstorming`, `code-reviewer`), so a name match is removed only when two things hold: the project shows the blueprint installed it (its plugin manifest, its `scripts/ship.sh`, its ship state files, a `hooks/hooks.json` that names only its handlers, or one of the skills only the blueprint ships), and the file itself is one the blueprint shipped, its content matching a version the blueprint released (line endings ignored). Anything else, another pack's file of the same name or a blueprint copy you edited, is listed as `unsure` and left alone; remove such a file yourself if it is the blueprint's. A project with no traces gets `nothing to migrate` and the skill stops.

The skill shows the report, checks that v4 is installed (it stops if the project would be left with no blueprint), then asks once: apply the list, apply it but keep `CLAUDE.md` as it is (the script then runs with `--keep-instructions` and touches neither instructions file), or stop. In a headless or unattended run nobody answers, so the default is to stop and change nothing (and to set the run state to `needs-human` when there is one), because a deletion cannot be undone.

It makes no commit. When it finishes it reports what was removed, moved and renamed, names the backup branch, and asks you to review the diff and commit it yourself (`chore: migrate to Agent Blueprint v4`).

## Step 3: remove the v3 plugin

Once no project needs the old skills:

```bash
claude plugin uninstall claude-code-blueprint@claude-code-blueprint
claude plugin marketplace remove claude-code-blueprint
```

The first command is the one ab-migrate prints. The second removes the old marketplace; per the Claude Code docs it also uninstalls any plugin left from that marketplace (<https://code.claude.com/docs/en/plugins/marketplace-reference>). The v3 installer registered the plugin by writing `enabledPlugins` in `~/.claude/settings.json` and the files under `~/.claude/plugins/`; if `claude plugin list` still shows the old plugin after both commands, remove the `claude-code-blueprint@claude-code-blueprint` key from `enabledPlugins` and restart Claude Code.

## Step 4: refresh the project files

Run the ab-project-start skill in the migrated project. Its `scripts/scaffold.py` copies the v4 scaffold into the project without overwriting anything:

- files the project lacks are created, for example `docs/context/CONVENTIONS.md`, `GOALS.md` and `STATUS.md`, `BACKLOG.md` and `.agent-blueprint/.gitignore`;
- the renamed `AGENTS.md` keeps every section it has and gains only the v4 template sections it lacks;
- a `CLAUDE.md` that lacks the `@AGENTS.md` line gets it at the top; the one-line `CLAUDE.md` from Step 2 is kept as it is;
- `.gitignore` files gain only the lines they are missing.

It prints one line per file (`created`, `merged` or `kept`). Ask for a dry run first if you want to see the list before it writes.

## What moved

| v3 | v4 |
|---|---|
| 29 agents in `agents/`, each a Claude Code agent file with its own `effort:` tier and tool list; listed by `/agents` | Prompt files under `skills/<skill>/references/agents/`, read by the skill that dispatches them. There is no `agents/` directory and no `/agents` listing, per-agent tool limits are gone, and a helper inherits the session's model and effort instead of a fixed tier. In a host without subagents the skill follows the prompt file itself |
| Working files under `.claude/` | `.agent-blueprint/` in the project root: `plans/`, `review-runs/`, `team/`, `run/`, `debug/`, `forensics/` and `cache/`, with its own `.gitignore` that keeps `run/`, `team/`, `review-runs/` and `cache/` out of commits while plans and notes stay tracked. Worktrees default to `~/.agent-blueprint/worktrees/<project>/` |
| Session Continuity block in the instructions file | `docs/context/STATUS.md`; skills write the instructions file only in the explicit learnings step |
| `CLAUDE.md` | `AGENTS.md`, which every host reads; `CLAUDE.md` holds the single line `@AGENTS.md` for Claude Code |
| Slash commands (`/ship-pipeline`, `/quick-fix`, and the rest) | Skills are named in prose (the ab-ship-pipeline skill), and every host also picks a skill from its description. Explicit invocation differs per host; see the table below |
| `hooks/hooks.json` with 10 handlers, Claude Code only | `hooks/claude-code.json` (the same 10 handlers) and `hooks/codex.json` (SessionStart, PreToolUse on `Edit` and `Write` and on `Bash`, PostToolUse, Stop). The other six hosts get no hooks and lose only the session-start pointer to `STATUS.md`, the injection scanner on writes, the commit-message check, the ship-pipeline Stop guard and the Agent Teams gates; no pipeline depends on them |
| `scripts/ship.sh` copied into the project | `skills/ab-ship-pipeline/scripts/run.sh --host <host> "<feature>"`, run from the installed skill; nothing is copied into the project |
| The `<promise>DONE</promise>` sentinel in the loop's output | `.agent-blueprint/run/state.json` with a `status` field (`running`, `done`, `blocked`, `needs-human`); the runner never reads completion from printed text |
| `.claude/ship-*.local.md` and `.claude/team-active.local.md` | `.agent-blueprint/run/` (`state.json`, `pr-body.md`, `commit-msg.md`, `provenance/`, `logs/`) and `.agent-blueprint/team/`. Each pipeline skill's `provenance/<skill>.json` lists its helper steps as `{step, path: helper\|inline}`, the shape the smoke test reads; `.agent-blueprint/.gitignore` is created by the working-folder step, not by the provenance step |
| `.claude/blueprint.local.json` for the commit-format hook's opt-in | `.agent-blueprint/config.json` in the project or in `~/.agent-blueprint/` |

## Instruction rules

The v3 `CLAUDE.md` and template were rewritten as principles with reasons, and `docs/upgrade/v4-instruction-rules.md` lists every hard rule from v3 with where it lives now. Most are kept as a principle or enforced by a gate, hook or the template `.gitignore`. Five were dropped because current models do them by default or they no longer apply: "ALWAYS read a file before editing it", the Analysis Paralysis Guard, "Files under 500 lines", "DRY, YAGNI", and the plugin-provided counts ("53 skills, 10 hooks") in the template.

## Legacy installs

A project set up with `install.sh --legacy` has flat copies of the v3 skills, agents, hooks and `scripts/ship.sh` inside it. The flag is retired: `bash install.sh --legacy` now prints a message and exits 2 without changing anything. Run the ab-migrate skill on the project; it recognises those copies by name and removes them the same way as the plugin traces above.

If you want v4 without a plugin system, `bash install.sh --copy-dir <dir>` copies the 53 skills into any folder and keeps an install record there, so a later re-run removes skills that were renamed or deleted. Each host's support note under `docs/hosts/` says where that host reads skills from.

## Rollback

The backup branch `blueprint-v3-backup` holds the project as it was before the migration; check it out or cherry-pick from it to restore files.

To reinstall v3.8.0, re-add the old marketplace pinned to the v3.8.0 tag (GitHub redirects the old repository name to the renamed one, and without the pin you would get the v4 marketplace), then install the old plugin id:

```bash
claude plugin marketplace add Ninety2UA/claude-code-blueprint@v3.8.0
claude plugin install claude-code-blueprint@claude-code-blueprint
```

The `owner/repo@ref` form is per the Claude Code docs (<https://code.claude.com/docs/en/plugins/marketplace-reference>). Do not leave v3 and v4 enabled at the same time: two sets of the same skills load, and the v4 session-start hook warns about it in every session until one is removed.
